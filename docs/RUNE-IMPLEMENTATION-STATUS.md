# Rune rebuild: implementation status and shipping gates

Snapshot: **23 November 2026**. This document compares the current checkout with the [cross-platform plan](RUNE-CROSS-PLATFORM-PLAN.md). It records implementation and observed evidence separately. The plan remains the acceptance contract; its unchecked tasks must not be treated as completed merely because corresponding code now exists.

The repository now contains a substantial Rust/Rune application, native adapters for both target platforms, portable policy/provider implementations, migration, packaging, and a signed-download verifier. **It remains a development build. Public macOS and Windows shipping readiness has not been demonstrated.** Controlled cross-app Windows capture/reading now has hosted native evidence, while the supported-device feasibility gate remains open for the required Mac and Windows 11 client matrix.

**Current scope decision (23 November 2026):** the user chose to keep this a development build. Production publisher accounts, signing/notarization, update hosting and publication are deferred. Their absence does not block delivering the development candidate; they remain requirements for any later public release. Known native compatibility and model-quality limits remain documented rather than implied to have passed.

## Lifecycle candidate following `f9927c9`

The lifecycle implementation addresses the confirmed launch, shutdown and context-navigation defects. The actual Tokio runtime is owned separately on the main thread; shared Services retain only its handle. Shutdown cancels admission, confirms complete runtime destruction (including nested blocking tasks), then confirms geometry-worker completion. Each serial writer stage has a five-second budget after the event loop/monitor stop. This is not a bound on prior OS/GPU teardown. An unsafe timeout exits immediately while retaining the instance lease until process death. Safe cleanup retains the lease through a fixed AppKit/Win32 error dialog; only acknowledgment permits ordinary release. Runtime construction is fallible, and panic unwinding terminates before the lease can be released while an independent writer may remain. App-owned diagnostics/presentation use fixed messages; the pinned Rune dependency can still print its own graphics error to stderr.

Late context completion uses the same request/policy checks without activating Reader, resizing, committing a newer preview or rearming scrolling. Completion during a settings write retains its queued action until the outcome is known. Explicit reading actions still activate Reader. Runtime/token regressions cover Settings, Saved/History, consent, stale callbacks, pending-save outcomes and cancellation on teardown.

Windows browser registration now uses in-process Win32 registry APIs. External transcription creates the child atomically inside a non-inherited kill-on-close Job Object, with an explicit inherited pipe-handle list. There is no spawn-then-assign interval; failure to establish containment refuses the operation before PCM is sent. Windows-native fixtures cover descendants surviving normal child exit, job closure and forced parent termination. These causal fixtures and the installed failure/recovery probes passed in Windows CI at `c90c268`. In both optimized startup reports, the sole owned action control was a visible enabled `Button` with ID **2**, not 1; acknowledgment and actual app exit code 1 were verified. The control ID alone does not establish its caption or the MessageBox return value.

Before the helper correction, local workspace formatting, strict Clippy and **299 tests, two ignored** passed, including 181 app tests. The Mac native-alert fixture verifies fixed content/main-thread guards without displaying a dialog; portable PowerShell startup fixtures verify data-retention and child-environment contracts. These results do not establish execution of the new Windows-only process semantics or an actual Mac failure dialog.
